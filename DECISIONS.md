# Architectural decisions

## P0 and P1

- **Separate simulator and Inquest:** simulator internals and truth are kept under `simulator/`; Inquest runtime modules have no simulator imports or truth-file access. Export IDs are opaque and scenario/fault labels are stored only in the truth artifact.
- **Versioned contracts:** each exported record carries `schema_version: "1.0"`. Pydantic v2 models reject unknown fields and unsupported schema versions instead of coercing their meaning.
- **Simulation time:** scenario timestamps derive only from a fixed UTC start and simulation offsets. Configured per-service clock skew is applied to emitted source timestamps and retained as uncertainty; no wall clock affects generated behavior.
- **Determinism:** one `random.Random(seed)` instance is used in stable service/time iteration order. No global random state is used.
- **Generative propagation:** each service's metrics are computed from load, local fault parameters, and dependency latency/error propagation. Values are not prewritten per service.
- **Stage isolation:** Plugins share only typed contracts and core services. The runner catches per-stage exceptions, saves `FAILED` status and traceback, passes typed missing-input data onward, and always serializes a validated final report.
- **Environment fallback:** The available interpreter is Python 3.12.14; Python 3.11 was not installed. Project metadata supports Python 3.11 and 3.12, and tests ran on 3.12. Dependencies unavailable in the managed runtime were installed into the writable workspace package target.
- **Pinned environment:** Exact versions of Pydantic v2, NetworkX, NumPy, Pandas, SciPy, Typer, PyYAML, and pytest are in `requirements.txt`. `setup.ps1` reuses the exact-version local cache offline, otherwise attempts installation. Python 3.11 is absent and Python 3.12.14 is used. The bundled interpreter's `ensurepip` fails, so the setup uses the workspace package cache rather than bootstrapping a venv.
- **Initial scenario:** a single seeded generative four-service scenario is used for P0. Its readable scenario and injected-fault labels occur only in the separate truth artifact, not the telemetry export.
- **Opaque ID construction:** Simulator scenario IDs are HMAC-SHA256 values over scenario key and seed using a randomly generated salt stored only under `simulator/sim_truth/`. This preserves same-seed reproducibility in a checkout and prevents deriving the scenario name from an export identifier.
- **Ingest boundaries:** Canonical JSON and YAML-mapped CSV are selected by an adapter registry. A malformed required manifest or unreadable source fails fast with file context; invalid individual rows are quarantined with row context so remaining valid evidence can be processed. Unknown references and clock/coverage conditions are warnings.
- **Vault integrity:** Each evidence item is canonically serialized and chained as `SHA256(previous_hash + canonical_json(item))`. Evidence is sorted by stable ID before append, so identical input yields an identical chain. Existing content is checked before extending; conflicting IDs fail instead of rewriting history.
- **Signal baseline and seasonality:** Each service/metric series uses median and MAD for a robust level baseline, with a 0.5% level floor and a 0.05 absolute scale floor to handle zero MAD. Seasonal medians are removed by time-of-day only when at least two full daily cycles are present. The simulator provides 20 hours, so seasonal correction is skipped and surfaced as a warning rather than inferred from incomplete cycles.
- **Change point:** CUSUM is the dependency-free default, with robust scale from first differences and explicit reset/interval adjustment across gaps. Ruptures PELT is selected automatically when installed. Both detectors implement one protocol and return the earliest accepted onset; confidence and timestamp uncertainty are recorded.
- **Missingness:** Missing windows stay absent. S00 and S02 report expected/observed coverage gaps; onset uncertainty expands across missing intervals instead of silently imputing samples.

## P2

- **Scenario dynamics:** Scenario variants share one parameter-driven service model and declared dependency graph. Fault service, activation interval/intensity, changes, observation duration, and telemetry omissions are inputs; service outcomes remain calculated from load, fault parameters, dependency state, and seeded jitter.
- **Holdout boundary:** The simulator and evaluator use explicit registries. `scenarios/holdout/` is reserved but not imported, listed, generated, tuned, or evaluated by default. The evaluation script reads truth artifacts only after Inquest has processed opaque-ID exports.
- **Seasonal normalization:** S02 assigns samples to phases from timestamps (so gaps do not shift phases). It only removes per-phase median offsets when the observation covers at least two complete daily cycles and at least 90% of phases have two observations. Otherwise it reports no normalization.
- **Candidate method plugins:** S03 has four independent method plugins selected by `candidate_methods` config flags. Plugin exceptions and missing evidence degrade the affected method without preventing the other methods from returning. Candidate provenance is checked against verified vault IDs before the stage returns.
- **Change-based relevance:** Change score combines exponential proximity to earliest onset with service relevance in the declared caller-to-callee topology. Changes after the onset are excluded, so a later restart that restores a service is not treated as the cause.
- **Graph walk:** Graph RWR seeds services by onset confidence and temporal priority, then walks caller-to-callee from observed symptoms toward possible shared dependencies. Topology and onset evidence only; no truth input.
- **Trace Ochiai:** Failing versus healthy trace coverage is compared with Ochiai. If traces are absent or one outcome class is missing, the method returns `DEGRADED` with a note and preserves any other method outputs.
- **Temporal lag:** Lagged Pearson correlation uses hourly latency pairs over declared edges only and tests lags zero through three. It reports correlation effect size `r`, not p-values; correlation is evidence for ranking, not proof of causality.
- **Ensemble:** Reciprocal-rank fusion combines per-method rankings by service, retains each method's raw score, unions evidence references, and reports top-rank disagreement as the fraction of methods outside the modal top candidate.
- **Evaluation protocol:** Default evaluation runs seeds 1–3 for every explicit non-holdout scenario and prints per-scenario top-1/top-3 before overall counts. No holdout results were examined or used to change scoring.

## P3 hardening: trace Ochiai diagnosis (before fix)

- The 0/18 top-1 and 0/3 clean top-3 result was first reproduced from the saved clean seed traces and S03 artifacts. The candidate score calculation already gave the database a positive score, but `TraceOchiaiMethod` appended candidates in `manifest.services` order and never sorted by score. The manifest order starts with checkout and ends with database; the evaluator correctly preserved this returned order, so checkout was ranked first regardless of score and the true service could fall below top three.
- Clean seed 1's recorded trace scores were checkout 0.0486, payments 0.0962, inventory 0.1430, and database 0.0962. Thus the root cause was a ranking-order bug, not an Ochiai threshold or absent vault evidence. This diagnosis preceded the fix. A minimal hand-built regression case will assert that a database-only failing-span signal ranks database first.
- No S03 numeric threshold or weight will be altered for this fix. The only change is sorting the existing scored candidates in descending score order, with target name as a deterministic tie-break.

## S03 tuning audit (P2 values)

Values below were selected during the initial S03 implementation or pre-evaluation scenario/unit checks. None was changed in response to the P2 evaluation table; the Ochiai fix changes ordering only.

- `change_based`: 2-hour symptomatic onset neighborhood; dependency walk depth cap 4; relevance 1.0 for a near-onset service, `0.5/(depth+1)` for a dependency, 0.15 fallback; 12-hour event lookback; exponential proximity scale 6 hours; uncertainty allowance from onset clock bounds. The dependency relevance multiplier was reduced from 0.8 to 0.5 before the full evaluation after the red-herring scenario test exposed an unrelated inventory deployment outranking the payments configuration event. This was before seeing the evaluation table and was a spec-driven relevance correction.
- `graph_rwr`: onset weight `confidence/(1+age_hours)`; PageRank damping 0.8, max iterations 100, tolerance `1e-10`. The edge direction was corrected before full evaluation after a manual clean-run showed the walk favoring checkout rather than its dependencies; no numeric values changed.
- `trace_ochiai`: no score threshold; score is `service_error_in_failing_traces / sqrt(global_failing_trace_count * (service_error_in_failing_traces + service_spans_in_globally_healthy_traces))`; candidate ordering bug fix is specified above. The formula and trace cohort were set before the full evaluation.
- `temporal_lag`: lags 0–3 hours, at least 5 aligned pairs, positive correlation only; Pearson `r` is reported as effect size. No p-value cutoff is used.
- `ensemble`: reciprocal rank fusion constant 60; disagreement is 1 minus modal top-candidate share. No score threshold.
- Shared candidate contract clamps scores below zero to zero, truncates rationale to 240 characters, and truncates SHA-256 candidate IDs to 12 hex characters; these are contract/output bounds, not evaluation-tuned parameters.
- Baselines: latest-change considers events no later than onset plus the maximum source-clock uncertainty; alert-order uses S02 service onset order. These definitions were fixed before the P2 evaluation rerun.

## P3b S04 frozen evaluation specification (written before S04 implementation and any S04 scenario evaluation)

- Per-check verdict vocabulary is lowercase `supports`, `contradicts`, or `inconclusive`. Every finding has a normalized effect size in [0, 1], one-line rationale, and only verified vault `evidence_ids`. Missing service telemetry or insufficient coverage must yield `inconclusive`, never `contradicts`.
- Per-candidate integrity passes only when the entire vault chain verifies and all S03 candidate evidence IDs exist in it. `verified` requires integrity pass, at least 2 independent supporting causal checks, and zero causal contradictions; vault integrity alone is not causal support. `contested` requires integrity pass plus any contradiction, or an equally good competing candidate. `insufficient_evidence` applies when integrity passes and checks are mostly inconclusive. `unsupported` applies on integrity failure, or contradictions without any support. “Mostly inconclusive” means inconclusive causal checks are a strict majority of enabled, completed causal checks; the vault-integrity check and unavailable/disabled checks do not enter this denominator. “Equally good” means same S03 score within absolute tolerance `1e-12`.
- S04 values/thresholds are frozen for Part C. `vault_evidence`: effect size 1 when every cited ID is present and 0 when one or more are absent; this is a binary integrity fact. `dependency_path`: effect size 1 for a recorded cause-to-symptom path and 0 for a complete graph with no path; a gap on the candidate service, a symptom gap when there is no positive path, or an empty graph is inconclusive. An affected candidate service is inconclusive even if graph edges exist. `temporal_consistency`: effect size 1 when a same-service event precedes onset within the sum of event and onset timestamp uncertainties, 0 when same-service changes occur only after onset; event/onset timestamps are the sole temporal inputs. `recovery_check`: requires 3 metric windows between onset and action and 3 after; uses median absolute baseline deviation normalized by `max(MAD, 0.05)`, and calls recovery only when pre-action deviation exceeds 1.5 MAD and post-action deviation is at most 1.5 MAD. Effect size is the fractional reduction in deviation, clamped to [0,1]. Three windows enforce minimum local coverage; the 1.5-MAD bound is the frozen near-baseline criterion. `alternative_check`: effect size is the candidate's fraction of symptomatic services reachable in the declared graph; a competing candidate contradicts when its covered count is >= the candidate's. This checks explanatory coverage, not probability. Missing telemetry yields `inconclusive`, effect size 0. Candidate scores within absolute tolerance `1e-12` count as equally good; this tolerance handles floating point equality. Status priority thresholds are >=2 causal supports and no causal contradictions for `verified`; any causal contradiction with some causal support is `contested`; strict majority of causal checks inconclusive is `insufficient_evidence`; causal contradictions with zero support or integrity failure is `unsupported`. Re-ranking priority is categorical status order, S03 rank stable tie-break. No threshold or constant may change after Part C absent a documented bug/spec correction.
- Re-ranking is configurable and defaults OFF. When enabled, status priority is `verified > contested > insufficient_evidence > unsupported`, with original S03 rank as stable tie-break. No status-based rank adjustment occurs when disabled.
- Independence/data audit: `vault_evidence` reads only candidate evidence IDs and vault integrity; `dependency_path` reads declared dependency edges and symptomatic service membership; `temporal_consistency` reads change-event timestamps, onset timestamps, and timestamp uncertainty only; `recovery_check` reads change events and raw metric windows before/after the action, testing all onset metrics independently; `alternative_check` reads the declared dependency graph and symptom set. None calls an S03 method, consumes S03 method scores, or consumes S03 lag-correlation outputs. Temporal consistency does not read latency values or temporal_lag results. Source records may overlap at the vault boundary, but computed signals and algorithms are independent.
- Recovery and alternative checks are specified generically from canonical change kinds, metrics, onsets, and declared dependencies; no scenario labels or simulator truth are inputs. If the available telemetry cannot support a check, it must return `inconclusive`.
- After the initial Part A draft and before any scenario evaluation, implementation review clarified recovery coverage from “3 post-action windows” to 3 pre-action plus 3 post-action windows, and made the intended comparison explicit: pre-action deviation >1.5 MAD and post-action deviation <=1.5 MAD. This was to make recovery measurable against both incident and recovery periods, not based on results. The relative-reduction effect-size definition was also made explicit. These are logged spec clarifications; no evaluation-informed tuning occurred.
- This specification was written before S04 implementation and scenario evaluation. The workspace initially had no Git repository; the requested local repo was initialized and the spec committed before the first evaluation as `59cade35196252bf5fa2549aa4f7b27e9e55106a`.

## P3b preliminary-run bug log (before corrected rerun)

- The first Part C run found three bugs; its tables are preserved as `eval/p3b_results_pre_bugfix.md` and are superseded. This was a correctness rerun, not threshold tuning. The run also revealed that vault integrity support must not count as causal support; that semantic interpretation has been logged and committed before the corrected run.
- **Recovery metric selection bug:** recovery inspected only the earliest onset metric for each service. In the restart case that metric was CPU, which did not return to baseline, while latency did recover after the restart. It produced false contradictions. The fix evaluates every onset metric independently; a supported recovery requires the frozen three pre-action and three post-action windows and the same 1.5-MAD rule. No threshold changed.
- **Telemetry-gap scope bug:** a gap in any symptomatic service forced dependency and alternative checks for every candidate to inconclusive. These were often isolated missing windows, not absent service telemetry. The fix makes a gap inconclusive for the affected candidate; a positive recorded dependency path can still support another candidate, while absent paths are never contradicted if candidate/symptom telemetry is marked missing. Missing traces are also represented as a service-level telemetry gap. The missing-data policy is unchanged; only its incorrect global application was fixed.
- **Integrity/causality classification bug:** `vault_evidence=supports` was counted as causal support. The vault check only proves citation integrity, not that a cited record supports the candidate as cause. It now gates integrity and is excluded from causal-support counts. `verified` still requires >=2 supporting causal checks and zero causal contradictions. This implements the stated status semantics; no threshold changed.
- Corrected rerun uses the same thresholds, candidate inputs, scenarios, and seeds. No other evaluation-informed changes are allowed.

## P3 stage: S04 verification

- S04 consumes only the S03 ensemble, its exported verification context, and the verified S01 vault. It never accesses simulator data or truth.
- `vault_evidence` checks citation existence in the hash-verified vault. `dependency_path` checks candidates against declared caller-to-callee edges, walking reversed edges from a proposed cause toward symptomatic callers. `temporal_consistency` compares candidate and earliest symptom onsets while respecting recorded clock uncertainty; absent onset data remains inconclusive rather than being treated as a rejection.
- Each check is independently toggleable under `verification_methods`; per-method findings are retained. Decision confidence is the fraction of active checks supporting its majority verdict; disagreement is the fraction of candidates with conflicting active verdicts. Finding and decision evidence IDs are checked against the vault.
- **S04 dependency direction correction (no tuning):** the first implementation traversed caller-to-callee while asking whether a proposed cause could reach symptomatic callers. Since recorded edges are caller -> callee, this was backwards for that question. It now traverses reversed edges (callee -> caller). This was a semantic direction bug found during code review, fixed before the final 51-test gate; no threshold, score weight, or constant changed. A hand-built payments -> database edge regression asserts that database is supported as the cause of symptomatic payments and that the edge ID is cited.
- S04 tests cover vault-backed output, per-method disabling, independent method modules, and dependency-edge direction. Holdout was not run and no P4 work was started.

## P4 Part B: frozen design specification (written before P4 implementation/evaluation)

### Fusion abstention

- Each S03 method contributes an item's rank only when that method emitted the canonical candidate with at least one evidence ID that passes the existing vault evidence contract. Otherwise it records an explicit per-method, per-candidate abstention reason (`no_candidate`, `no_evidence`, or `invalid_evidence`) and contributes no rank. This is candidate-specific; a method can rank supported candidates while abstaining on others.
- Reciprocal-rank fusion remains `1 / (60 + rank)` (`rank_constant=60`, unchanged). No absent-method worst rank is synthesized. Scores from methods that did return evidence remain visible per candidate; abstentions are emitted separately and do not erase raw method scores. Disagreement is recomputed over non-abstaining methods only and remains the fraction outside the modal top candidate. Candidate canonicalization, lexical deterministic tie-break, and score formula stay unchanged.
- Expected effect: reduce rank dilution when a method lacks candidate evidence, especially for silent roots with no local metrics or changes. It may harm cases where a method has sparse evidence but a useful rank; the nonempty, vault-valid evidence rule retains sparse evidence, so only actual evidence absence is abstention. The one-way/noisy alert and partial-graph validation cases are explicit risks because evidence availability differs across methods.

### S04 status and dependency semantics

- Vault integrity is a gate, not a causal vote. Integrity passes only if the whole chain verifies and every cited ID exists; failure yields `unsupported`, independent of other checks. `vault_evidence` stays in findings for auditability but is excluded from causal support/contradiction counts.
- `verified` requires integrity pass, at least two independent causal supports, and zero causal contradictions. `contested` requires integrity pass plus a causal contradiction or an equally good competing S03 candidate. `insufficient_evidence` means a strict majority of enabled causal checks are inconclusive. `unsupported` means integrity failure or causal contradictions with no causal support. Disabled checks are excluded from the denominator; ties are not a strict majority. Equal S03 scores use absolute tolerance `1e-12` (unchanged).
- A dependency path is necessary topology evidence, not sufficient causal evidence. `dependency_path` returns `supports` only if the candidate reaches symptomatic services and its reachable symptom count is strictly greater than every competing candidate service's count. Equal/shared ancestry is inconclusive rather than support. A complete graph with no candidate-to-symptom path contradicts; partial/empty graph or relevant telemetry gap is inconclusive. Graph completeness is explicit canonical collection metadata (`dependency_graph_complete`, default true for older exports), never inferred from scenario names. Its effect size is the candidate's reachable symptom fraction in `[0,1]`. The strict-greater condition addresses shared-ancestry decoys while preserving topology's role. It can reduce support for a true shared dependency when the graph is incomplete or another candidate reaches the same callers.
- Independence is by evidence family, not method name: `dependency_path` and `alternative_check` both use declared graph topology plus symptom membership and together count as at most one independent support. `temporal_consistency` contributes the event/onset timestamp family; `recovery_check` contributes metric-window recovery after a timestamped action. Vault integrity contributes no causal support. This prevents two graph calculations from manufacturing the two independent supports required for `verified`. Risk: a genuine cause with only graph evidence will remain insufficient rather than verified.
- S04 uses only canonical evidence, graph, event timestamps, metric windows, and onset data. It does not use scenario labels/truth, method scores, or temporal-lag correlation. Missing telemetry remains inconclusive, never a contradiction.

### Re-rank policy and frozen constants

- **Chosen policy: (a), status annotation only, no re-rank.** S03 order remains the actionable order and S04 retains statuses beside candidates. The previous full re-rank fell from 21/24 to 19/24 top-1 and produced five documented rank regressions. An annotation cannot demote a correct S03 result merely because a check is inconclusive. A later policy change would require a new approved phase and fresh validation.
- Frozen fusion values: RRF constant `60`; rank starts at `1`; abstain only when candidate evidence is absent or invalid under the existing vault contract; disagreement denominator includes only methods with a non-abstaining top candidate; ties break by canonical candidate string ascending. S03 method scoring constants are unchanged and are not tuned in P4.
- Frozen S04 values: integrity is all-or-nothing; verified support count `>=2` distinct evidence families; contradiction count for verified `0`; insufficient-evidence majority is strict (`inconclusive_count > enabled_causal_check_count / 2`); equal-score tolerance `1e-12`; dependency support requires strictly more reachable symptomatic services than each competing candidate; dependency effect size `reachable_symptoms / total_symptoms`; complete-graph no-path is contradiction; missing/partial topology is inconclusive.
- Retained S04 check constants: temporal consistency allows event/onset timestamp uncertainty summed in milliseconds and event-before-onset includes the uncertainty boundary; recovery uses `3` pre-action and `3` post-action windows, baseline scale floor `0.05`, and recovery thresholds `pre_deviation > 1.5 MAD`, `post_deviation <= 1.5 MAD`; recovery effect is fractional deviation reduction clamped to `[0,1]`. Vault finding effects remain binary (`1` valid, `0` invalid). All values above are frozen before P4 eval. There are no P4 score weights or thresholds set from a P4 table.
- No P4 evaluation has been run. This section is the frozen spec; any later correction must be a documented bug/spec fix, not score-led tuning.

### S04 comparative causal ordering

- Change: a path to symptoms is necessary topology but cannot by itself support a candidate. For a candidate with reachable symptomatic services, compare its earliest candidate-service onset to the earliest onset among those reachable symptoms using their existing timestamp uncertainty. If the candidate onset is later beyond combined uncertainty, `dependency_path` must not support it and reports `contradicts`; if timestamps or graph coverage are incomplete it reports `inconclusive`. It may support only when the candidate onset is no later than the earliest reachable symptom onset within combined uncertainty, and its existing unique-coverage rule passes.
- Change: `alternative_check` may `contradict` when another candidate reaches an equal or greater subset/count of symptomatic services and has a strictly earlier service onset beyond combined timestamp uncertainty. It supports only when the candidate is uniquely best by symptom coverage and is not temporally downstream of the symptoms it purports to explain. Ties without a reliable temporal ordering are inconclusive. Missing onset/telemetry is inconclusive, never a contradiction. Include the relevant graph-edge and onset-metric evidence IDs in the finding. This allows the red-herring database decoy to be challenged by earlier payments symptoms, while a genuine upstream root with an earlier onset remains eligible for support.
- Expected effect: reduce false causal support for shared-ancestry or downstream decoys, including red_herring_deploy. Risks: a real upstream cause whose telemetry onset is delayed/noisy may be contradicted; incomplete graphs or missing service onset will yield fewer decisive findings; shared dependencies with nearly simultaneous caller/root onsets will remain inconclusive.
- Frozen comparison constants: strict ordering uses combined event/onset timestamp uncertainty already represented in canonical data; “equal coverage” means `>=` on integer symptomatic-service count; no new numeric threshold. Preserve existing missing-data behavior, partial-graph behavior, vault integrity gate, and support-family independence. Do not alter the S04 status vocabulary or its thresholds.

### Fusion for silent_cause

- Change: retain reciprocal-rank fusion but apply a fixed method multiplier of `2.0` to graph_rwr's candidate contributions, with multiplier `1.0` for change_based, trace_ochiai, and temporal_lag. Formula: `sum(method_weight / (60 + rank))` over candidate ranks emitted with valid vault evidence; absent/invalid evidence still abstains. This recognizes the distinct upstream propagation signal: graph_rwr ranks the silent database root first in each development case, while other methods rank competing local symptoms first; the existing equal-weight sum lets those distributed local ranks bury the consistent upstream candidate. Preserve per-method scores, abstentions, disagreement, deterministic candidate string tie-break, and rank constant 60.
- Expected effect: elevate a graph-supported upstream candidate when its own telemetry is absent, which should help silent_cause. Risks: graph_RWR can be wrong on red_herring_hard, partial_graph, and shared_dependency; multiplying its vote can promote a shared-ancestry decoy. The fresh red-herring and partial-graph cases are explicit checks of this risk. This multiplier is frozen before seeds 4-6 are generated and evaluated.

### Ranking policy and frozen P5 constants

- S04 re-ranking remains **OFF**. S04 annotates candidates and cannot reorder the S03 output. The Part B comparative changes alter verdicts/statuses only; do not use them as a ranking signal.
- Frozen unchanged constants: RRF rank constant `60`; 1-based rank; lexical canonical-candidate tie-break; candidate evidence abstention only on absent/invalid vault-backed evidence; S04 status rules from P4 (integrity gate, at least two independent causal support families to verify, zero causal contradictions, strict-majority inconclusive rule, equal-score tolerance `1e-12`); dependency unique-coverage and effect-size formulas; recovery uses 3 pre/3 post windows, scale floor `0.05`, and `1.5 MAD` thresholds. P5's only new fusion weight is graph_rwr `2.0` (all other weights `1.0`); new temporal comparisons use timestamp uncertainty and integer coverage, without learned thresholds.
